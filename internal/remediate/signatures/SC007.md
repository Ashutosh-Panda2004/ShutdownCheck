# SC007 — READINESS_NOT_FLIPPED

**Stage S2 — flipping readiness.**

## What was observed

Your readiness endpoint kept returning a success status for the entire shutdown, right up until the process disappeared.

## Why it matters

Readiness is how you tell the orchestrator to stop sending you work. If it never changes, nothing upstream learns you are going away, and the load balancer keeps routing to you for a full probe interval — typically several seconds, and often longer than your whole shutdown.

The result is traffic arriving at an instance that is actively trying to leave. Depending on what else your service does, that surfaces as `SC005`, `SC003`, or a burst of 502s once you do close the socket.

This is also the cheapest of all shutdown bugs to fix: it is usually one boolean.

## How to fix it

On `SIGTERM`, set readiness to failing **first**, before anything else in your shutdown sequence. Readiness is a statement about whether you should receive new work, not about whether the process is alive — those are different questions and belong on different endpoints.

### Go

```go
var ready atomic.Bool
ready.Store(true)

mux.HandleFunc("/readyz", func(w http.ResponseWriter, _ *http.Request) {
    if !ready.Load() {
        w.WriteHeader(http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
})

<-sigterm
ready.Store(false)   // before the sleep, before the drain
```

### ASP.NET Core

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<ReadinessCheck>("ready", tags: new[] { "ready" });

app.MapHealthChecks("/readyz", new HealthCheckOptions {
    Predicate = c => c.Tags.Contains("ready")
});

lifetime.ApplicationStopping.Register(() => ReadinessCheck.Ready = false);
```

### Node.js

```js
let ready = true;
app.get('/readyz', (_, res) => res.sendStatus(ready ? 200 : 503));
process.on('SIGTERM', () => { ready = false; /* then drain */ });
```

### Spring Boot

Readiness is built in; make sure the probes are enabled and that shutdown moves the state:

```properties
management.endpoint.health.probes.enabled=true
management.health.livenessstate.enabled=true
management.health.readinessstate.enabled=true
```

Spring publishes `AvailabilityChangeEvent` with `ReadinessState.REFUSING_TRAFFIC` during graceful shutdown.

## Check your probe configuration too

Flipping readiness only helps if the orchestrator notices in time. With the defaults below, it can take up to 10 seconds to react:

```yaml
readinessProbe:
  periodSeconds: 5
  failureThreshold: 2
```

Tighten `periodSeconds` for services that terminate quickly, and remember that this detection delay is part of why the lame-duck window in `SC006` exists.

## A common trap

Do not point readiness and liveness at the same handler. If readiness failing also fails liveness, the kubelet will restart the container you are trying to shut down.
