# SC002 — SIGKILL_REQUIRED

**Stage S7 — clean exit inside the budget.**

## What was observed

The process was still running when the grace period expired, so it had to be killed outright. ShutdownCheck sent the `SIGKILL` itself, exactly as your orchestrator would have.

## Why it matters

`SIGKILL` cannot be caught or deferred. Whatever the process was doing at that moment simply stops: in-flight requests die, buffered writes are lost, and background work is abandoned part way through.

There is a second cost that is easy to miss. Every deploy now takes the full grace period per instance, because the orchestrator waits out the clock before killing each one. A rolling deploy across twenty pods with a 30 second grace period spends ten minutes waiting for processes that were never going to exit.

## Working out which failure this is

`SC002` is a symptom with three common causes, and the rest of the report tells you which:

| Also reported | Cause |
|---|---|
| `SC001` | Nothing reacted at all — there is no signal handler. |
| `SC005` | The listener never closed, so the drain never had a chance to finish. |
| Neither | The drain started but ran past the budget. |

## How to fix it

### There is no handler

The default disposition for `SIGTERM` is to terminate, so a process with no handler dies instantly — which is `SC001`, not this. If you are seeing `SC002` alone, a handler exists but never completes.

A frequent cause is the process not being PID 1 in its container. A shell wrapper such as `CMD npm start` or `CMD ./run.sh` receives the signal itself and does not forward it:

```dockerfile
# The shell gets the signal; your app never sees it.
CMD npm start

# Exec form: your process is PID 1 and receives it directly.
CMD ["node", "server.js"]
```

### The drain never finishes

Something in the shutdown path is waiting on work that will not complete. Usual suspects:

- Idle keep-alive connections that are never closed, so `server.close()` never calls back (Node.js, in particular).
- Long-polling, server-sent events or websocket connections with no deadline.
- Background workers with no cancellation.

Give the drain a hard deadline of its own that is comfortably shorter than the grace period, and force an exit when it lapses:

```go
ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
defer cancel()
if err := srv.Shutdown(ctx); err != nil {
    log.Printf("drain timed out, exiting anyway: %v", err)
}
```

Exiting slightly early on your own terms is better than being killed on someone else's, because you at least control what gets abandoned.

### The budget is simply too small

If the drain is genuinely correct and just needs longer, raise the grace period rather than shortening the drain:

```yaml
terminationGracePeriodSeconds: 60
```

Keep the ordering intact:

```
preStop sleep  +  drain timeout  <  terminationGracePeriodSeconds
```
