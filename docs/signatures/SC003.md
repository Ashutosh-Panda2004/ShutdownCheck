# SC003 — IN_FLIGHT_DROPPED

**Stage S6 — draining in-flight work.**

## What was observed

Requests that were already being processed when `SIGTERM` arrived did not complete. The server was mid-flight on real work and abandoned it.

## Why it matters

This is the headline defect. Every one of those requests is a user who got an error, and it happens on **every deploy, autoscale-down and node drain** — not occasionally, but each time.

It is also close to invisible. The requests fail from the client's side, so your own error rate may look fine; the loss shows up as a small blip that gets filed under "deploy noise" and never root-caused.

Check the failure breakdown in the report, because the shape tells you which mistake you made:

| Failure | What it means |
|---|---|
| `reset` | The socket was destroyed mid-response. You closed connections instead of draining them. |
| `eof` | The process exited while the response was still being written. |
| `timeout` | The connection stayed open but nothing came back. Often a drain that waits on something that never finishes. |

## How to fix it

Close the listener, then wait for outstanding requests to finish before exiting. Do not close active connections, and do not call `os.Exit` from your signal handler.

### Go (net/http)

`Shutdown` does exactly this: it stops accepting, then waits for active requests.

```go
ctx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
defer cancel()
if err := srv.Shutdown(ctx); err != nil {
    log.Printf("drain did not finish: %v", err)
}
```

Use `Shutdown`, never `Close` — `Close` breaks active connections immediately, which is this bug.

### ASP.NET Core

The default shutdown timeout is five seconds, which is often shorter than the slowest request:

```csharp
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(25));
```

### Node.js (Express)

```js
server.close(() => process.exit(0));   // waits for in-flight requests
```

`server.close` does not close idle keep-alive sockets on older Node versions, so track and end idle connections yourself, or the callback never fires and you get `SC002` instead.

### Python (Gunicorn)

`graceful_timeout` must exceed your slowest request, and must fit inside the orchestrator's grace period:

```
gunicorn --graceful-timeout 25 --timeout 30 app:application
```

### Java (Spring Boot)

```properties
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=25s
```

## Getting the budget right

The drain timeout must be **shorter** than the orchestrator's grace period, or you will be hard-killed part way through draining and trade this bug for `SC002`. A workable ordering is:

```
slowest request  <  drain timeout  <  grace period
```
