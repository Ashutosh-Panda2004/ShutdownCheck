# SC006 — NO_DEREGISTRATION_WINDOW

**Stage S3 — the lame-duck window.**

## What was observed

Your service closed its listening socket almost immediately after receiving `SIGTERM`.

## Why it matters

This is the failure almost everyone gets wrong, because it is what the usual advice tells you to do.

Removing an instance from a load balancer is **asynchronous and concurrent with signal delivery**. Nothing guarantees the routing tables are updated before your process receives the signal:

```
kubelet                  SIGTERM ─────────────▶ your process   (immediate)
endpoints controller     pod removed from Endpoints
kube-proxy / mesh / LB   routing updated ...................... (eventually)
```

In practice the routing update lands hundreds of milliseconds — sometimes seconds — *after* your process is told to stop. Every request that arrives in that gap hits a closed socket, gets `connection refused`, and your ingress turns it into a **502 for a real user**.

So a service that shuts its listener the instant `SIGTERM` arrives did graceful shutdown exactly by the book, and still drops traffic on every single deploy.

## How to fix it

Fail readiness immediately, then **keep serving** for long enough that de-registration can propagate, and only then stop accepting.

The order matters:

1. `SIGTERM` arrives.
2. Readiness starts failing at once, so the orchestrator begins removing you.
3. **Keep accepting and serving new connections** for a few seconds.
4. Stop accepting.
5. Drain what is in flight.
6. Exit.

### Kubernetes

The idiomatic place for the wait is a `preStop` hook, which runs *before* `SIGTERM` is delivered:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 5"]
terminationGracePeriodSeconds: 30
```

Your grace period must comfortably exceed the pre-stop sleep plus your worst-case drain time, or you trade this bug for `SC002`.

### Go (net/http)

```go
<-ctx.Done()             // SIGTERM
readiness.Store(false)   // step 2
time.Sleep(5 * time.Second) // step 3: keep serving
srv.Shutdown(context.Background()) // steps 4 and 5
```

### ASP.NET Core

Fail the readiness probe from `IHostApplicationLifetime.ApplicationStopping`, and give the host room to drain:

```csharp
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(30));
```

Kestrel does not implement the wait itself, so the delay belongs in your `preStop` hook.

### Node.js

```js
process.on('SIGTERM', async () => {
  ready = false;                                  // step 2
  await new Promise(r => setTimeout(r, 5000));    // step 3
  server.close(() => process.exit(0));            // steps 4 and 5
});
```

## When this is not a bug

If nothing sits in front of your service — no load balancer, no ingress, no service mesh — there is no routing to propagate and closing immediately is correct. Run with `--profile strict` and this signature drops to informational.
